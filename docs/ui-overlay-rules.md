# 浮层组件规范（Overlay Rules）

> 适用范围：`android/app` 手机端、`android/tv` 电视端、`android/shared`。
> 判红实现：`scripts/check_appearance.py` 第 6／7 条。
> 建立日期：2026-11-07。起因是审查发现同一仓库里有两套弹窗通路，且 25 处色值绕过令牌。

## 为什么要先定义「有哪些浮层」

把所有浮层统称「弹窗」，后果是每次来一个需求就临时造一个：该用 Toast 的用了 Modal，该留撤销入口的用了二次确认，该用 Drawer 的用了弹窗。用户感知到的就是「打断太多」和「信息一闪就没」。

按**打扰程度从轻到重**分六类，先定类，再选实现。

## 一、分层与选型

### Tooltip — 悬停解释

只做鼠标悬停时的名词解释，移走即消失。**不得承载关键信息**：触屏与遥控器上没有 hover，等于没写。

### Toast — 操作结果反馈

只用于「刚才那个动作成功了／失败了」这类**事后无需再找**的反馈：发送成功、已复制、已删除。

**不得**用于：
- 用户必须读到的信息（权限缺失、连接失败原因）；
- 事后还要能找到的信息（TV 端「显示在其他应用上层」的权限引导——那是常驻提醒，不是一次性提示）；
- 需要用户做选择的内容。

### Alert — 常驻系统提醒

页面顶部的醒目条（黄条／红条），用于**持续存在**的系统状态：状态页的降级提示、传输通道异常、权限未授予。

选它的判据是「这条信息在问题消失前都应该看得到」。用完即走的不算。

### Modal — 模态弹窗（`ApComponents.DialogCard` / `ApDialog`）

**只留给不可逆操作**：删除文件、清空自定义键位、退出全屏控制台。

必须满足：操作后数据无法找回。能做到「撤销」的，一律不做二次确认（见下方防坑二）。

### Popconfirm — 气泡确认框

挂在触发元素旁的小确认层，用于**列表内高频删除**（路节目录、键位条目、收到的文件列表）。

判据是「一屏内可能连续删好几条」——每次删除都盖一层全屏蒙层，用户要重复「点确定 → 蒙层消失 → 再找到下一行」，这是最典型的体验损耗。本仓库的落地形态是行内联动的 `ApDialog`，不要为每条都开独立 Modal。

### Drawer — 抽屉

用于**边看边改**：设置页的多分组编辑、皮肤与强调色的实时预览。改完仍然看得见背后的列表。

判据是「用户操作时需要与背后的列表左右对照」。

### 新页面 — 彻底切换业务流程

只有在下单支付、完整的账号流程这类「离开当前上下文才算合理」的场景才跳新页面。不要为了省事把长表单塞进弹窗。

## 二、宽度与形态判据

| 内容量 | 形态 | 宽度 |
|---|---|---|
| 少（两三行 + 一两个按钮） | 常规弹窗 | 400 |
| 中（一列表单、5–8 行） | 常规弹窗 | 520 |
| 多（两列、带说明） | 常规弹窗 | 720 |
| 长表单 / 深度内容 | Drawer 或新页面 | 按容器 |

本仓库 Compose 侧的落点是 `ApComponents.DialogCard`：它已封顶 `fillMaxWidth(0.94f)` 与 `widthIn(max = 560.dp)`，并按内容收缩（`heightIn(max = 62% 屏高)` + `verticalScroll`）。需要别的档位时改调用方的 `modifier`，不要在页面里另画一个卡片。

## 三、三条防坑（写进约定，不是建议）

### 防坑一：表单类弹窗禁用「点蒙层关闭」

含输入控件的弹窗（键映射编辑、模板编辑、手动 IP 输入）**不得**设 `setCanceledOnTouchOutside(true)` / `onDismissRequest` 里直接收。用户手滑一次，已填内容全丢。

同时要**加草稿自动保存**：编辑中的值落到 `ApAppearancePrefs` 同级的偏好文件里，下次打开回填。

### 防坑二：可撤销的操作不做二次确认

普通删除（能通过「撤销」恢复的）直接执行，配一个撤销入口（Snackbar + 撤销按钮，5 秒内有效）。

只有**数据无法找回**的高危操作才用 Modal 强提醒：清空全部自定义键位、删除整个接收目录、退出并断开受控设备。

### 防坑三：按钮文案写具体动作

用户对弹窗按钮的注意力只有几百毫秒。禁止「确定 / 取消 / 是 / 否」，一律写具体动作：

- ✅「放弃退票」「确认扣费并退票」「删除 3 个文件」「清空键位」
- ❌「确定」「是」「OK」

按钮文案走 `strings.xml`（`ui_common_*` 里已有的通用词只在「取消 / 关闭」这类真通用场景用），不要内联中文字面量。

## 四、本仓库特例（与通用规范冲突时以这里为准）

### 1. 触控板页与键盘页是全屏手势面

`TouchpadPage` 与 `KeyboardPage` 的操控区是**全屏手势面**，任何叠加的按钮、Toast、浮层都会吃掉手势或遮挡命中区。

- 不得在这两页的操控面上叠加悬浮按钮／浮层；
- 需要反馈时走页面外的常驻区（顶栏胶囊、状态行），不要用 Toast 压在手势面上；
- 键盘页的编辑入口用页内 `DialogCard`（`KeyboardPage:279`），不要改成 Activity 级弹窗。

### 2. 电视端不得用 Toast 承载权限引导

TV 端「显示在其他应用上层」这类权限引导，用户需要**事后能找到入口**。用 Toast 等于一闪就没、事后无处可寻。

正确形态：状态页的常驻提示条（Alert 层）+ 可点击跳转设置的入口。已有实现见 TV 浮窗的权限检测与可见引导。

### 3. 焦点态与 5 秒自动收起遵守既有实现

电视端遥控器导航依赖焦点环：新增浮层必须给出可见焦点态，且**不得**自行改动 5 秒自动收起的时序。要改先看 `TvOverlay` 的现有实现，那是真机验收过的。

## 五、实现落点

| 层 | 落点 | 说明 |
|---|---|---|
| Compose 侧 | `ui/miuix/ApComponents.kt` 的 `DialogCard` | 已带缩放、insets、入场动效、限高滚动 |
| View 侧 | `ui/ApDialog.kt` 的 `builder` / `confirm` / `items` / `customView` | 统一 `ApPalette.dialogStyle()` |
| 色值 | `res/values/colors.xml` + `res/values-night/colors.xml` 的 `overlay_*` / `module_state_*` | 页面里不得出现 `Color(0x…)` |

**禁止**把 View 侧的 `AlertDialog` 改写成 Compose 的 `Dialog`：`FilePanelActivity`、`HotkeyBoard`、`CustomKeyboardDialog`、`TouchpadActivity`、`RemoteActivity` 都是 `ComponentActivity` 的 View 树，没有 Compose 宿主，套过去会直接崩。

## 六、判红规则

`scripts/check_appearance.py` 第 6、7 条（2026-11-07 新增，基线零豁免）：

1. `ui/` 目录下出现 `Color(0x…)` 字面量 → 失败；
2. 出现裸 `androidx.compose.ui.window.Dialog(` 或 `AlertDialog.Builder(`（未走统一封装）→ 失败。

白名单只有两个文件：`ui/compose/ApComponents.kt`（Compose 侧封装本身）与 `ui/ApDialog.kt`（View 侧封装本身）。新增豁免必须在关卡常量里写明「为什么不走封装」。
